DAM AI Agent — Meeting Briefing

Purpose: everything you need to answer confidently during the live test. Skim sections 1–3 before walking in; sections 5 and 6 are the ones that matter when he starts probing.

1. The pitch

If he says "tell me what you built" (30 seconds)

"The African Development Bank has an internal document, the Delegation of Authority Matrix, that defines who can approve, check, review, initiate, or must be informed for every activity the Bank does. It's over 250 pages of wide tables with sideways column headers and a coded notation. It's technically searchable and practically unusable. I built a system that parses it into a knowledge graph and answers plain-language questions about it — with a hard guarantee that it never invents a fact, because for a compliance document a confident wrong answer is worse than no answer."

If he asks for more (2 minutes)

Add these three points, in this order:

  • The extraction was the hard part. PDF is a page-description format. It says which character is drawn where, not what it means. Column headers are rotated 90°, footnote digits are fused against authority codes, and text bleeds across row boundaries. Every one of those had to be solved with geometry, not guesswork.
  • The graph is the model. 327 activities and 131 roles connected by 2,108 edges. "Who approves X" is a graph traversal, not a text search.
  • The LLM is on a leash. It never decides what the facts are. It receives facts already retrieved from the graph and only rephrases them, and the output is checked word-by-word against those facts before display. Fails the check → the answer is thrown away and a deterministic template is shown instead.

3. How it works — the five steps

  1. Extract. pdfplumber gives characters and words with coordinates, fonts, and sizes. Character-level access is required, not convenient — the superscript rule depends on per-character vertical offset and font size.
  2. Parse. Eight stages: rows → task blocks → title/reference cleaning → code geometry → role attribution → node assembly → validation. Each stage is separately inspectable, which is how every bug got localised.
  3. Model. Build a networkx directed multigraph. Multigraph because one role can hold several distinct responsibilities over the same activity. Three edge types: contains (hierarchy), responsible_for (role → activity, carrying the code), references (cross-references).
  4. Retrieve. ID fast path first (exact, confidence 1.0). Otherwise TF-IDF + cosine similarity over activity titles, with a deterministic typo-correction pass before matching.
  5. Answer. Deterministic template built from graph records → optional LLM rephrasing → grounding check → display. Metadata shown alongside: resolution method, confidence, whether the LLM was used.

5. Hard questions — and how to answer them

"This is a Data Science Master's. Where's the machine learning?"

Most likely question. Don't get defensive — answer structurally:

"The data science is in four places. The retrieval model is TF-IDF vectorisation with cosine similarity over the activity corpus. The modelling phase produced a knowledge graph, 459 nodes and 2,108 edges, which is the representation everything queries. There's a substantial data engineering pipeline, eight stages from raw PDF geometry to a validated node set. And there's an applied LLM layer with a grounded-generation architecture.

What there isn't is a supervised model, and that was a deliberate decision rather than an omission. There is no labelled data — no query/answer pairs, no annotated tables — so training one would have meant inventing a ground truth and then evaluating against my own invention. For a compliance document where errors are silent and plausible, a rule I can trace to a measured character offset is worth more than a classifier I can't interrogate."

"How do you know the extraction is actually correct?"

"There's no ground-truth dataset, so I couldn't compute precision and recall against one — and fabricating that table would have been the dishonest option. What I did instead: every record I claim was checked by comparing it against the printed page it came from. The 374 tests aren't coverage-driven; almost every one exists because a specific bug was found on a real page, and the test pins the fix so it can't come back silently. The 0.56% unresolved-role rate measures coverage of role attribution. And I verified live through the actual HTTP endpoint before trusting any change."

"Why TF-IDF? Why not embeddings or a fine-tuned model?"

"The corpus is about 330 short titles in a controlled institutional vocabulary — small, static, and using the words users actually type. Embeddings win when you have a large, varied corpus and enough domain data to tune them. Here they'd add a model download, inference cost, and an external dependency, in exchange for recall I wasn't losing. TF-IDF scores are also explainable: I can trace a match to shared terms and diagnose a bad one. Given retrieval accuracy is the foundation everything else sits on, being able to explain why a node came back was worth more than marginal recall."

If he pushes: concede honestly that a hybrid lexical + semantic layer is the right next step for questions phrased in outside vocabulary, provided the grounding check stays unchanged.

"Why not just upload the PDF to ChatGPT?"

"I tried reasoning through exactly that. When you flatten this document to plain text, the meaning is destroyed — a rotated header becomes a stray string disconnected from the codes underneath it, so a retrieved passage can contain the activity name and the letter A without preserving which role that A belonged to. The model then produces something plausible from text that already lost the answer. And it has no notion of being wrong: it returns fluent text either way. For who-holds-financial-approval-authority, that's the failure mode you can't accept."

"Explain the grounding check." (He will probe this — it's the centrepiece.)

"The model never sees the graph and never chooses what to retrieve. It gets the question, the facts already retrieved, and a prompt telling it to state them naturally and invent nothing. But a prompt is a request, not a guarantee. So before any generated sentence reaches the user, every role name in the backing facts is checked for presence in the generated text. It's a containment test, not a similarity judgement, so a paraphrase can't satisfy it — rename a role, merge two, or drop the third of four informed parties and it fails, however fluent it reads. On failure the generated answer is discarded and the deterministic template is shown. Comparison normalises whitespace and case, which I added after it was rejecting faithful rephrasings over nothing but spacing."

Follow-up he may ask: "Doesn't that fire constantly?" — Yes, it did at first, and the cause was mine not the model's: the prompt asked for 1–3 sentences, and activities with many responsibilities can't be stated completely in three. The model obeyed brevity and dropped facts; the check correctly caught it. I relaxed brevity when the fact count crosses a threshold, and left the accuracy criterion untouched. The requirement that needed adjusting was never the accuracy one.

"What happens if the LLM is unavailable?"

"Everything still works. The LLM only phrases answers. Set the mode to Off and you get the deterministic template answers with every lookup capability intact — ID resolution, text search, typo correction, redirects, glossary, refusals. There are three modes plus Auto, which falls back cloud → local → template."

Offer to demo it: flip the picker to Off mid-meeting and re-ask question 1.

"Why a graph and not a database?"

"The questions are relationship questions. 'Who approves this' is a traversal along one edge type, and 'what does this role approve' is the same traversal reversed — both single operations on a graph, both joins or scans on a flat structure. I used a directed multigraph specifically because one role can hold several distinct responsibilities on the same activity, so two nodes may be connected by several parallel edges each carrying its own code. And at runtime there's no database at all: the knowledge base is read-only, fits in memory, and is versioned with the code as a build artefact."

"Tell me about a bug you found and how."

Good story, use the informed-marker one:

"The '(i)' informed marker was never matching. The code scanned for a consecutive run of '(', 'i', ')' — but on real pages that marker renders as five separate characters, so it never matched anything. 174 of 276 records in an early version had an informed marker printed in the document with no role ever attached in my data. It was completely invisible in any output that didn't compare records against the actual page. I confirmed it against 2.126's real characters on page 24 before changing a line."

Even better if he asks about failures: mention the split-row fix you rejected. The first attempt was a general merge rule; checking it before adopting showed 1,614 candidate merges document-wide, several clearly wrong. Rejected it, replaced it with a narrow rule that only merges a band when its content is entirely authority codes.

"How would you scale it to the full document?"

"Same pipeline, more pages. The remaining chapters use the same table conventions as far as I can tell, so it's mainly a test of whether the rules generalise — which is untested, and I'd treat any assumption otherwise as exactly the kind of guess this project is built to avoid. The processing side is not the constraint: the full rebuild takes 15–20 seconds and the whole document is a few megabytes, which is also why I didn't reach for Spark. The hard part was never computational, it was interpretive."

"What would you do differently?"

"Two things. I'd extract the footnote text at the same time as the footnote numbers instead of deferring it — I'll come back to that. And I'd write the whole-document consistency checks earlier. The hierarchy bug where children were derived by string prefix matching was invisible for a while and was eventually caught by a consistency check, not by inspection. If that check had existed from the start it would have caught the bug the day it was written."

6. Limitations — say these before he finds them

Volunteering these reads as rigour. Being caught out on them reads as the opposite.

The footnote gap (newest, and the most likely thing he'll trip over in a live test).

Footnote numbers are extracted and attached to each responsibility, and answers surface them — you'll see "(footnote 3)" next to a role. But the footnote text at the bottom of the page was never extracted, so the system can't tell you what footnote 3 says. Ask it and you get nothing useful.

If he finds it: "Correct, and I know why. The schema has a Footnote model with scope, number, and text, but the parser behind it was never built, because there's an unresolved question I refused to guess at: does footnote numbering reset per process or per chapter? Get that wrong and footnote 3 in one chapter silently resolves to the wrong footnote 3 somewhere else — a plausible-looking error of exactly the kind this project exists to prevent. Answering it means checking real pages where the numbering restarts. It's the first thing on my list."

Why this matters, and say so: footnotes carry the conditions on authority — delegation ceilings, prior-approval requirements. An answer naming an approver while dropping "up to USD 5 million" is true and misleading at once.

  • Scope. 79 of 250+ pages, three chapters. State it up front rather than letting him discover it.
  • Two records with empty titles (2.516, 2.522) the parser couldn't recover, plus one residual title corruption (2.222.1). All documented, not hidden. For 2.222.1 a candidate fix was implemented, tested, found not to fix the target case, found to cause a regression elsewhere, and reverted — leaving a documented defect beat carrying a change that made extraction worse overall.
  • Retrieval is lexical. A question phrased entirely in vocabulary the document doesn't use will resolve poorly.
  • No version awareness. The system reflects one version of one document and has no mechanism to detect that the DAM has been revised — a real operational concern, not a theoretical one.
  • Free-tier hosting sleeps after inactivity, so a cold first request is slow.
